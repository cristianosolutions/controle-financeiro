## Defeitos confirmados

### QA-01 — Alta: fatura paga desaparece, mas mantém débito

1. Criar conta com saldo inicial de R$ 1.000 e cartão.
2. Registrar compra de R$ 100 no cartão.
3. Pagar a fatura usando a conta: saldo passa a R$ 900.
4. Excluir a compra por `DELETE /api/transactions/:id`.
5. Consultar `GET /api/cards/:id/invoices` e `GET /api/accounts`.

**Obtido:** exclusão HTTP 204, lista de faturas vazia e saldo ainda em R$ 900. O pagamento continua persistido, mas deixa de aparecer na lista de faturas, prejudicando a conciliação e o acesso ao estorno pela interface.

**Esperado:** preservar a fatura e seu histórico de pagamento ou bloquear/conciliar explicitamente alterações em compras de faturas pagas. Não ocultar um pagamento que continua afetando o saldo.

**Localização:** `backend/src/routes/transactions.ts:187` permite a exclusão sem conferir pagamento; `backend/src/routes/cards.ts:27` constrói a lista de faturas somente a partir das compras existentes.

### QA-02 — Média: exclusão de conta com pagamento de fatura retorna 500

1. Manter pelo menos duas contas ativas.
2. Pagar uma fatura com uma conta sem lançamentos diretos, aportes ou transferências.
3. Excluir essa conta por `DELETE /api/accounts/:id`.

**Obtido:** HTTP 500. O banco rejeita a exclusão com `P2003`, restrição `CardInvoicePayment_accountId_fkey`.

**Esperado:** erro de negócio, por exemplo HTTP 422, explicando que a conta possui pagamentos vinculados e pode ser desativada para preservar o histórico. A conta não foi excluída no teste.

**Localização:** `backend/src/routes/accounts.ts:68`. A verificação de vínculos considera lançamentos, aportes e transferências, mas não pagamentos de faturas.

### QA-03 — Baixa: observações não preservam exatamente o texto informado

1. Criar lançamento com `notes` igual a `"  texto livre  "`.
2. Inspecionar o campo retornado.

**Obtido:** `"texto livre"`, sem os espaços das extremidades.

**Esperado:** preservar a escrita original, conforme o contrato descrito no README no momento do teste. A revisão documental posterior passou a explicitar essa limitação; o código continua sem correção. Não foi constatada alteração de letras ou acentos neste cenário.

**Localização:** `backend/src/routes/transactions.ts:21`, uso de `.trim()` no campo `notes`.

### QA-04 — Média: JSON malformado é tratado como erro interno

1. Enviar `POST /api/auth/login` com `Content-Type: application/json` e corpo `{`.

**Obtido:** HTTP 500, mensagem genérica de erro interno. O parser identifica `entity.parse.failed` com status 400, mas o middleware substitui esse status.

**Esperado:** HTTP 400 para erro de sintaxe no corpo enviado pelo cliente.

**Localização:** `backend/src/middleware/error-handler.ts:26`, fallback incondicional para 500 quando o erro não corresponde às classes tratadas.
